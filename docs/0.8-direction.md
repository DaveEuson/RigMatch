# 0.8 direction

Written 2026-08-26, with 0.7.1 staged and not yet tagged. Everything here came
out of Dave testing 0.7.1 on real machines and asking four questions in a row.
Deliberately deferred so 0.7.1 stays a patch release — the Jetson reading 0 GB
is live right now and should not wait on feature work.

## The through-line

Every item below is the same failure in a different place: **a check, a filter
or a label that does not say what it actually did.**

0.7 was about the app not passing on a model's claims about itself. This is the
same principle turned inward — the app not passing on its own claims about
itself.

---

## 1. Setup says "You're all set!" when it is not

The strongest of the four, and the only one that is an outright false statement.

The Simple Mode setup card checks Ollama, the graphics card and disk space, then
says **You're all set!**. Pick "create an image from a prompt" as your goal and
that sentence is untrue: the program that makes images is not installed, has not
been looked for, and is not mentioned.

0.7.1 already fixed the two places this surfaces *later* — the goal tile now says
"needs ComfyUI", and the download refusal offers to find it rather than naming a
Settings panel Simple Mode does not have. But both are downstream. Setup is
where a person is told whether their machine is ready, and it answers a narrower
question than the one it appears to answer.

**What it should do:** when the chosen goals include a ComfyUI runtime, setup
looks for ComfyUI too, and says what it found — the same way it reports Ollama.
`locateComfyFolder()` in `src/lib/comfyTransport.ts` already does the search and
the verification; it is one call.

**The obstacle:** `SimpleWizard` does not currently know which goals were picked.
It receives `initialDream` for opening PICK on the right filter, and nothing
else. That needs threading through before the check can be conditional — and it
should be conditional, because someone who only wants a chat model should not be
told about a program they will never need.

## 2. "Rig Picks" is a filter nobody recognises, including its author

Dave asked for a "Good Fit" filter. It exists. It is the **Rig Picks** button,
its internal id is `fits-vram`, and it was showing 149 models in the screenshot
he sent while asking for it.

If the person who wrote the app does not recognise his own filter, the name is
wrong. That is about as clean a signal as usability testing ever produces.

One idea currently carries five names:

| where | word |
|---|---|
| filter label | Rig Picks |
| code | `fits-vram` |
| size badges | Sweet spot / Small pick / Too big |
| filter help text | close fits |
| what the author called it | Good fit |

**What it should do:** pick one word for "this model fits your machine" and use
it everywhere — filter, badge, help text, and the code. "Good fit" is the one
Dave reached for unprompted, which is the strongest argument available.

Worth being careful: `modelFitsVram` includes close fits (up to 1.15× VRAM, with
RAM assist), so the word has to cover "fits with help" and not only "fits
comfortably". "Sweet spot" and "Small pick" are doing real work distinguishing
*how* it fits; the filter is answering *whether*. Two levels, not five words.

## 3. More columns on the model table — the data already exists

Asked for: **Date Added** and **Most popular**. Both are surfacing work, not
gathering work.

- `pulls` is already on every row, is already a `ModelSortKey`, already drives a
  "popular" badge at ≥500,000, and already has a `popularity-meter` component in
  `ScoreVisuals.tsx`.
- `modifiedAt` is already captured — from Ollama's `modified_at` and LM Studio's
  `created` — in `electron/main.cjs`.

**Two decisions this forces, and they are the interesting part:**

**Date Added is empty for most of the table.** It exists for installed models
only. With 16 installed of 322, that column is blank in 95% of rows. Either it
shows only when filtered to Installed, or it needs a second meaning for
catalogue rows (when the model was released?) — which is a different column
wearing the same name.

**Popularity is the one number on that table that is not about your machine.**
Pull counts are global Ollama downloads. Every other column — Match, Speed, Fit,
Status — is local evidence, which is the entire pitch. A column called "Most
popular" reads as a verdict RigMatch reached. It did not; it read a number off a
server. Name it for what it is (*Downloads (Ollama)*) so it cannot be mistaken
for a local measurement.

## 4. Check Local produces no evidence it ran

In Advanced Mode the local status card shows a title, a detail line and a
**Check Local** button. Pressing it rescans, spins briefly, and returns to a
card identical to the one before. On a fast machine that is a flicker.

Compare Simple Mode's **Check my computer**, which produces a result card naming
three specific findings. Same action, and only one of them tells you what it
learned.

**What it should do:** report the scan. What was found, and when — a timestamp
alone would be an improvement over nothing, because the current failure is that
you cannot tell the button worked.

## 5. Carried over: accuracy versus speed is never asked

Not from this round of testing, but from the same conversation, and it is the
largest of the five.

The Match Score is a fixed blend: quality `0.34`, speed `0.32`, finish rate
`0.18`, fit `0.16`. It never varies — not by goal, not by preference.

Two consequences:

**A slow, excellent model structurally cannot win.** Work it through: a 70B at
100 quality and 20 speed scores 40.4 on those terms; a 7B at 75 and 95 scores
55.9. Someone who picks "Writing" because they want the best prose their machine
can produce gets handed the fastest acceptable model instead, and is never told
that is what happened.

**The largest weight is the least reliable signal.** `scoring.ts` says so itself:
quality is "derived from heuristic/regex checks — treat it as a directional
proxy, not a ground-truth quality measurement". Speed is a stopwatch. They are
blended nearly 1:1 and presented as a single number. Cloud judging makes quality
real, and is exactly the path most people will not enable.

**What it should do:** the goals splash already asks what you want to do. The
natural companion is *"and what matters more — the best answer, or the fastest
one?"* with presets that reweight.

**Why this is not a small change:** it alters what "winner" means. Saved scores
would need the weights they were computed under, which is what `SCORE_VERSION`
exists for, and every existing scorecard becomes "retest recommended". That is a
release headline, not a patch.

---

## What is deliberately not here

The four items above are all *interface honesty*. None of them is a new
capability, and that is the point — 0.7 added a lot of surface, and the testing
that followed found the seams rather than gaps.

Before adding anything new in 0.8, the ComfyUI setup path deserves finishing
end-to-end: goal → setup → download → generate, with the app telling the truth at
every step. 0.7.1 fixed three of those four steps. Setup is the one left.
