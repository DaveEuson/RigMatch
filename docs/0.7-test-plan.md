# Testing 0.7 before it ships

Scoped to what changed since 0.6. Everything else has automated cover — 790
tests, 22 sweep checks, a 41-check desktop gate, a clean screen audit and a
clean layout sweep across sixteen window sizes. What follows is the part no
script can reach.

**Run the portable build, never the installer.** `release/win-unpacked/RigMatch.exe`.
The NSIS installer shares a GUID with your real copy and would evict it.

Each item says what to do and what *should* happen. Where the wrong outcome is
one this release specifically fixed, it is named — if you see the old behaviour,
the fix did not take.

---

## 1. Clear Data — the one with a credential in it

The most consequential change in the release, and the easiest to get wrong.

1. Get a key saved first. The field is **not in Settings** — it lives in the
   run dialog: start a benchmark, and the cloud-judging section has
   **OpenRouter API key**. Paste anything (`sk-test-123`; it is never sent),
   then cancel the run. Add a model note somewhere, and note which mode you
   are in.

   That the field is only reachable from a dialog you were about to dismiss is
   itself worth a thought — it was written for the moment cloud judging is
   offered, and it is the one setting a person would go to Settings to clear.
2. Settings → Advanced → **Scoring & Reset** → **Clear All Data** → confirm.

Should happen:
- Scores, history, chat, notes and goals gone.
- **The API key field is empty.** In 0.6 it survived.
- **You are still in Advanced Mode.** In 0.6 you were dropped into Simple.
- **The getting-started guide does not reappear.** In 0.6 it did.
- Your Ollama models are untouched.
- The dialog you confirmed said all of the above before you pressed it.

Then **restart the app** and check the mode and the guide again — both used to
come back on the next launch even when the immediate behaviour looked right.

Extra: clear your logs first (Scorecards → the bin icon), then immediately clear
data. It used to fail with "Could not clear all data" and clear *nothing*,
because the log clear is rate limited.

## 2. Chat telling the truth

With any ordinary text model selected (llama3.2, qwen2.5 — not gemma4):

| Type this | Should happen |
|---|---|
| `draw me a picture of a cat` | A note *before* the reply: this model writes text, it cannot make images, and where image generation lives |
| `transcribe this recording` | A note saying it cannot listen, and that asked anyway it would write a plausible transcript of nothing |
| `make a video of a rocket` | A note pointing at the Video test |
| `how do I draw a flowchart in mermaid` | **No note.** An ordinary question must not be nagged |
| `what is the capital of France` | **No note** |

Then switch the model to **gemma4:e2b** and ask to transcribe again — there
should be **no note**, because that model genuinely hears. A warning that fires
when it need not is how people learn to ignore warnings.

## 3. Chat making the picture — needs ComfyUI running

With ComfyUI up and an image checkpoint loaded (sdxl-turbo):

1. Ask `draw me a picture of a lighthouse at sunset`.
2. The note should now *offer* rather than signpost, with a **Generate it here**
   button.
3. Press it. Expect: a rising seconds counter, a **Stop** button that stays
   clickable, and then the picture in the conversation. About 6–15s on
   sdxl-turbo.
4. Do it again and press **Stop** midway. Expect "Stopped after Ns. Nothing was
   saved." and no image.

Worth trying deliberately: **stop ComfyUI and ask again.** The offer should
disappear and the note should go back to signposting Advanced Mode. An offer
that cannot be honoured is the failure this whole feature is built to avoid.

## 4. The graphics card warnings

1. Start something GPU-heavy (a game — Civilization did it last time).
2. Open Advanced → **Activity**. Within a few seconds a note should appear
   saying the card is busy, *before* you click anything. It takes 3–5s because
   reading the card is slow.
3. Run a Listening test anyway. The running line should say the card is busy.
4. In chat, ask for a picture and press Generate. Same warning in the running
   line, from the first second.

Then close the game and repeat step 4 — **no warning should appear**. The
reading is taken before RigMatch loads the card itself, so it should not blame
you for ComfyUI's own work.

## 5. The microphone

Advanced → Activity → Listening → Audio: **Read a script aloud**.

- If you have more than one input, a **Microphone** dropdown should appear.
- Record, and check the transcript matches. Read the script *word for word* —
  the score compares against it, and improvising marks the model down for
  hearing you correctly. There is now a line on screen saying so.

## 6. RigMatch Chat making pictures — the new one

This is the feature you actually asked for, and no person has pressed the button
yet. It needs RigMatch running: the companion asks it to generate rather than
driving ComfyUI itself.

Open RigMatch, then open RigMatch Chat from the sidebar button.

1. Type `a lighthouse in a storm` and press **Make image** (beside Send).
2. Expect: "Asking RigMatch to make this...", then a rising seconds count, then
   the picture in the conversation with the saved path beneath it.
3. Check the file is really in `Pictures\RigMatch\`.

Then the three ways it should fail well:

- **Close RigMatch and press Make image.** It should say RigMatch is not running,
  not hang or fail silently.
- **Stop ComfyUI and try again.** It should say no checkpoint that can draw is
  loaded. This is the one I got wrong the first time — the offer appeared, was
  pressed, and could never have worked, because the first checkpoint on this
  machine is a video model with no text encoder.
- **Close and reopen the companion.** The picture becomes its filename rather
  than an image, and the path is still shown. That is deliberate: the
  conversation file stores the path, not a quarter-megabyte of PNG. The file is
  still on disk.

Worth noticing rather than testing: whether **Make image** belongs beside Send at
all, or whether it should be somewhere less prominent. It is a chat window that
can also make pictures, not an image tool with a chat attached, and the button
currently argues for the second reading.

## 6b. Knowing what the models can do

Open RigMatch Chat and look at the left panel *without hovering anything*.

- **What do you want to do?** should sit above the model list, with chips:
  Anything · Write · Read a picture · Hear audio · Make a picture.
- Each chip should narrow the list. Models that can look at pictures carry a
  **sees** chip; gemma4:e2b and e4b carry **hears**.
- Click **Make a picture** and every chat model should drop out, replaced by an
  **IMAGE MAKER** card naming the actual ComfyUI checkpoint — *sdxl-turbo* —
  and saying Ready or Not ready.
- Click that card: it should open a workspace with its own prompt box, not a
  conversation.

The thing being tested is whether you can answer "which one makes an image?"
by looking. The honest answer is *none of them* — that is ComfyUI's job, run by
RigMatch — and the maker card exists to say so while still being findable where
people look for it. An earlier version explained this in a paragraph, which was
accurate and unread.

If the chips are missing entirely, RigMatch has not sent its model list yet;
give it a moment after RigMatch finishes scanning.

## 6c. Two RigMatch windows

Found while testing this release, and worth confirming the fix.

1. With RigMatch already running, launch `RigMatch.exe` again.

The second one should **not** open a window — the first should come to the
front instead.

Then the case the lock does not cover, if you can make it happen (a second copy
with its own data directory): opening RigMatch Chat from a window that lost the
link should say **another RigMatch is already running** and tell you to close
the other one. It must not say "companion not found", and it must not open a
companion wired to the other window.

This mattered more than it looks. Both instances answered on the same port, so
RigMatch Chat listed one window's models and saved the other window's pictures,
and nothing anywhere said so. It cost me an hour of chasing a bug that was not
there: two measurements disagreed while both were correct, because they were
reading two different processes.

## 6d. Handing the companion a picture or a recording

New, and it did not exist in any form before — the companion could not take an
attachment at all, while listing models tagged *sees* and *hears*.

Open RigMatch Chat and pick **gemma4:e2b**.

- An **Attach a recording** button should appear beside the message box.
- Attach any audio file, ask what is in it, and expect a transcript.
- Now pick a model that only writes — **the button should disappear entirely.**

That last step is the point. The button is driven by what each model reports
over the bridge, not by what a file dialog would allow, so a text-only model
gets no offer rather than an error after the fact.

Also worth knowing before it surprises you: reopen the conversation afterwards
and the attachment shows as its filename rather than its contents. The bytes are
held for the session only — a recording is close to a megabyte encoded, and the
conversation file is rewritten on every change.

Do not use **gemma4:e4b**. It reports that it can hear and cannot actually
transcribe in this Ollama build; see §5.

## 6e. The chat dock, writing as it goes

Also new. The dock has always waited for the whole answer with nothing on
screen, and could not be interrupted.

In the app's own chat dock — not the companion — ask for something long:
*"count from one to forty in words, one per line."*

- The answer should appear **as it is written**, not all at once at the end.
- **Send should become Stop** while it writes.
- Press **Stop** midway: it should halt immediately and keep the text that had
  already arrived, with no half-word left dangling.

Streaming covers ordinary Ollama chat. An attachment or LM Studio still answers
in one piece, which is deliberate rather than overlooked.

## 7. The one I could not test — please do this one

**Stop a download mid-flight.** Queue a model you do not have, start the
download, and press Stop while it is genuinely downloading.

Should happen: it stops, the queue does not start the next model, and the UI
says it stopped.

This is the only behaviour in the release with no automated cover. The control
logic behind it was rewritten this cycle — two booleans held twice over became
one value — and while the rules are unit tested and the abort path is proven
against real Ollama, the button itself has never been pressed by a person. If
anything in 0.7 is going to be wrong, this is where I would look first.

## 9. The other two machines

RigMatch has shipped macOS and Linux builds since 0.6.0 and **nobody has ever
launched one**. The release workflow builds five targets; that is not the same
as any of them working. These are the highest-value checks in this document
because they cover the largest untested surface.

### Jetson (Ubuntu, ARM64)

Your own release checklist calls ARM64 experimental until smoke-tested on real
hardware. This is that test.

1. Does the AppImage or `.deb` **launch at all**?
2. **Does it read the graphics card?** This is the one I would bet on failing.
   Shared-memory detection matches on the GPU's model string — `orin`, `tegra`,
   `xavier`, `thor` — and Jetson often has no `nvidia-smi`, using `tegrastats`
   instead. If the name comes back empty, RigMatch will treat shared memory as
   discrete VRAM and the busy-card warnings will misfire.
3. Does **Your Rig** show sensible numbers, or zeros?
4. Does RigMatch Chat launch from the app?

### M4 Mac

1. **Gatekeeper.** The release body tells people to right-click and choose Open.
   Does that work exactly as written? If not, the instructions are wrong for
   everyone who downloads it.
2. **Unified memory** is detected by platform and architecture there rather than
   by name, so it should be sound — but does the fit advice read sensibly with
   no discrete VRAM figure?
3. Does the **companion inside the DMG** launch? It is bundled by an `afterPack`
   hook, which is its own never-exercised path.
4. Ollama on Apple Silicon uses MLX — are models still detected and scored?

Neither blocks the Windows release. Both decide whether the Mac and Linux
artifacts already on the Releases page are real.

## If something is wrong

Tell me what you did and what you saw, not a diagnosis — several bugs this cycle
looked like one thing and were another. The GPU warning that looked broken was a
3–5 second probe. A transcript that looked like confabulation was the script not
being read. What you observed is the useful part.
