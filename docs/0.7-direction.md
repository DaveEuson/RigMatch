# 0.7 direction

Written 2026-08-17, straight after 0.6.0-beta shipped.

## The ask

Bring the capabilities that currently live in the Lab — image generation, video
generation, transcription — **into the chat**, so a person talks to a model and
it does the thing, rather than hunting for the panel that does it.

And the constraint Dave put on it in the same breath, which is the harder half:

> we need to make sure we restrict what the models are capable of

## Why the restriction is the whole feature

RigMatch already knows more about model capability than most tools, because it
has to: `canHearAudio`, `canSeeImages`, `generationKind`, the capability filters
in the model list, the greyed-out skill tests in the run composer. That
knowledge exists because of a bug class this project keeps hitting — offering an
action where its precondition is unmet.

Chat is where that gets dangerous, because chat has no obvious edges. A person
types "make me a picture of a dog" at a text-only model and gets either a
refusal, a hallucinated description, or a confident lie. Today's Lab avoids this
by only showing a skill test when a model reports the capability. Chat has no
equivalent.

Two failures observed in 0.6 that predict this:

- **The listening test.** `gemma4:e2b` reports `audio`, accepted a real
  microphone recording, and returned *"I have a boy named Jack and a girl named
  Charlotte"* — an entirely unrelated sentence, not a mishearing. Reporting a
  capability is not the same as having it. The app scored it 6/100 and said
  MISS twice, which was the right answer, but only because the listening test
  measures against a known reference. Chat has no reference to measure against.

- **The video claim.** Selecting "A video maker" told the user "No contestants
  can make video on this PC" while two video models sat in the catalogue. The
  grid excluded them by design and the copy turned that into a claim about the
  hardware. In chat, the same mistake becomes a model confidently answering a
  question it cannot actually perform.

So the 0.7 work is not "add generation to chat". It is: **make capability a
first-class thing the chat surface reasons about**, then let the features
follow.

## What that probably means

1. **One capability model, not four.** `canHearAudio`, `canSeeImages`,
   `generationKind` and the dream-filter tags are four partial views of the same
   fact. Chat needs one authority it can ask: what can *this* model actually do,
   and how confident are we — reported by the provider, or measured by a run?

2. **Reported vs measured, kept apart.** `gemma4:e2b` reports audio and fails at
   it. A capability the model claims and a capability RigMatch has *watched it
   do* are different grades of evidence, and chat should prefer the second.
   RigMatch is the only app in this space that has the measurements.

3. **Route, don't refuse.** "Make me a picture" to a text model should not be a
   refusal — it should hand off to a model that can, or offer to. The Closet and
   the catalogue already know what is installed.

4. **Say the edge before the user hits it.** The composer greys out a skill test
   and says why. Chat needs the equivalent, in-line and before the send, not an
   apology afterwards.

## Also carried into 0.7

- **App.tsx is ~12,100 lines** after 0.6 removed 475. Every state bug found this
  cycle lived in it. Splitting it is worth more than any single feature.
- **Two features called "Listening"** — the composer's sample-clip test and the
  Activity card's microphone test. Renamed in the composer for 0.6, but the
  duplication is structural and will come back.
- **The glib advisory** (`docs/advisory-glib-variantstriter.md`) now ships in the
  Linux builds. Unreachable, but decided rather than fixed.
